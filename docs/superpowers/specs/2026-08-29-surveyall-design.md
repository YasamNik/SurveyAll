## 2. Architecture

### Stack

- **Next.js (App Router)** — web client and API in one TypeScript project.
- **Postgres 17 in Docker** — defined in the repo's `docker-compose.yml`. The app
  knows the database only through `DATABASE_URL`; local container, home server, and
  managed Postgres are interchangeable by changing that one value.
- **Drizzle ORM + drizzle-kit** — schema declared in TypeScript
  (`lib/db/schema.ts`), SQL migrations generated by `drizzle-kit` and committed to
  git, TypeScript types derived from the schema. One tool owns schema, migrations,
  and types.
- **Auth.js (NextAuth v5)** with the Drizzle adapter — Google OAuth + email magic
  link, database sessions.
- **Deploy target:** the owner's home server running the same compose file (app +
  Postgres + `cloudflared`), published through a free Cloudflare Tunnel.
  Cloudflare Workers via OpenNext stays open as a later app-hosting option; note
  Workers cannot open raw TCP to a home-server Postgres (would need Hyperdrive or a
  move of the DB), so that door has a known cost.
- **Web now, native later** — unchanged.

### Repo shape — layered single app

```
app/
  (app)/                    authenticated author UI
  s/[slug]/                 public survey respond page
  e/[slug]/                 public scheduling grid
  api/v1/                   HTTP adapter — the future native app's contract
lib/
  domain/                   pure TS: surveys/, scheduling/, shared/
  db/                       drizzle schema, client, queries
  auth/                     Auth.js config
drizzle/                    generated SQL migrations (committed)
docker-compose.yml          postgres + mailpit (dev profile) + app + cloudflared (prod)
```

**Import boundary (unchanged in spirit):** `lib/domain/**` imports nothing from
`next/*`, `react`, `drizzle-orm`, `next-auth`, or `@auth/*`. Enforced by ESLint
`no-restricted-imports` in CI.

The web UI calls the domain layer directly on the server; no self-HTTP hop.
Monorepo still rejected; `git mv` door still open.

### Security model — server-mediated, tested at the boundary

All data access goes through the server via the domain layer. **RLS is gone with
Supabase; server mediation is the authorisation model.** The discipline RLS testing
bought is kept one layer up: an integration suite at the adapter/domain boundary
proves the same negatives (anonymous cannot read a draft survey; author B cannot
read author A's surveys; results 403 without the toggle; raw answers never leak
through public endpoints).

**Operational consequences:**
- `DATABASE_URL`, `AUTH_SECRET`, SMTP credentials, `IP_HASH_SALT` are server-only.
- Postgres is never published through the tunnel: in production it has no exposed
  port; only the app container reaches it on the compose network.
- Connection pooling is a non-issue: one long-running Node container with one shared
  `pg.Pool` (via Drizzle) is the complete answer. Do not add pgbouncer unless the
  Workers path is taken.

## 3. Data model

Domain tables unchanged from §3 of the 2026-08-27 doc **except identity**:

- **`profiles` is dropped.** Auth.js (Drizzle adapter) owns `users`, `accounts`,
  `sessions`, `verification_tokens`. The `users` table already carries `name`,
  `email`, `image`; domain foreign keys (`surveys.author_id`,
  `survey_responses.user_id`, `schedule_events.author_id`,
  `schedule_participants.user_id`) point at `users.id`. No trigger needed — the
  adapter creates the row.

Count: 4 auth tables + 8 domain tables (surveys, questions, question_options,
survey_responses, answers, schedule_events, schedule_participants,
availability_slots). All reasoning about options-as-a-table, partial unique
indexes, availability rows, and participation-history-as-a-query carries forward
unchanged.

## 5. The foundation cycle

Six deliverables, each with a verification. Environments are now exactly two:
**local** (compose: postgres + mailpit; app via `pnpm dev`) and **production**
(server: full compose behind the tunnel). There are no preview deploys; that loss is
accepted for a solo project.

### 1. Repo scaffold + compose

Next.js App Router, TypeScript `strict`, Tailwind, ESLint + Prettier, pnpm, the
import-boundary rule, and `docker-compose.yml` with Postgres 17 (named volume) and
Mailpit. `.env.example` lists every variable.

**Verified:** `pnpm typecheck && pnpm lint && pnpm build` clean; a deliberate
`import { cookies } from 'next/headers'` inside `lib/domain/` fails lint;
`docker compose up -d` yields a reachable Postgres and Mailpit UI.

### 2. Auth

Auth.js with Drizzle adapter: email magic link (SMTP → Mailpit locally) and Google
OAuth (config present; activated when the Google client exists). Database sessions.
Middleware guards `(app)/*`.

**Verified locally:** request magic link → open it from Mailpit → land in `(app)`;
`users` row exists; sign-out clears the session; anonymous `(app)` redirects.
**Deferred verification:** Google sign-in end-to-end, once the OAuth client is
created (prerequisite list, §7).

### 3. Schema + migrations

Full schema in `lib/db/schema.ts`; `drizzle-kit generate` migrations committed;
migrations run programmatically at app start-up in production (one idempotent
migrate step before the server binds) and via a script locally.

**Verified:** migrations apply in order on a clean database; types compile; the
**authorisation integration suite** (the §2 negatives) passes against a real
Postgres.

### 4. CI

GitHub Actions on every PR: typecheck, lint, domain unit tests (Vitest),
migrations + authz integration tests against an ephemeral Postgres service
container, and one Playwright smoke (home → magic-link sign-in via Mailpit API →
reach `(app)`).

**Verified:** a PR that breaks the import boundary, or an authz negative, goes red.

### 5. Deploy — server + tunnel  *(replaces the Vercel deliverable)*

Production compose file (app, Postgres, `cloudflared`) on the owner's server; a
Cloudflare Tunnel bound to a stable hostname on an owned domain; deploy procedure
documented in the repo (pull → build → `docker compose up -d`). Nightly `pg_dump`
to a compressed file, few-day retention, copied off the machine (rclone to any free
remote) — deliberately minimal, the data is non-critical, but the stance is written
down rather than omitted.

**Verified:** open `https://<hostname>/api/v1/health` from outside the network;
complete a magic-link sign-in in production; restore one backup file into a scratch
database successfully.

**Blocked on prerequisites** (§7): domain on Cloudflare, server access, production
SMTP provider. Everything else in the cycle proceeds without it.

### 6. Thin vertical slice — *unchanged*

`GET /api/v1/health` + one `(app)` page, both through `lib/domain` → db.
**Verified:** real data through both adapters, locally and (once deliverable 5
lands) in production.

## 7. Prerequisites and operational gotchas

**Prerequisites for deliverable 5 (deploy) — none block deliverables 1–4, 6:**
1. A domain added to Cloudflare (free tunnels get random `trycloudflare.com` URLs,
   which would break the Google redirect URI and every shared survey link).
2. Google OAuth client in Google Cloud Console, redirect URIs
   `https://<hostname>/api/auth/callback/google` and the localhost equivalent.
3. A production email provider for magic links (e.g. Resend free tier); Mailpit is
   dev/CI only.
4. Physical/SSH access to the home server.

**OneDrive — now stricter.** Unchanged for `node_modules`; additionally the
Postgres data directory must be a Docker **named volume**, never a bind mount under
a synced folder, or sync will corrupt the database. The Linux machine's working
copy is on plain local disk (verified 2026-08-29); the Windows copy must be moved
out of OneDrive before any install or `docker compose up` there.
